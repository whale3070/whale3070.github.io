对所有系统执行取证镜像（取证映像制作）

conducting forensic imaging of all systems

对所有系统执行取证镜像（取证映像制作）

拆解术语（网安/电子取证场景）

  • forensic imaging：取证镜像（电子取证核心操作）
    不是普通复制文件，是按位（bit-by-bit）对磁盘/存储做只读克隆，生成镜像文件（如E01、dd镜像），保留原始数据、删除痕迹、分区、空闲空间、未分配扇区，保证原始证据不被篡改，具备司法效力。
  • all systems：全部系统（服务器、终端、工控机等涉案/待取证主机）

一句话解释

把所有涉事系统的硬盘做一份符合取证规范的原始镜像，原始设备封存不动，后续分析全部在镜像上操作，防止污染证据。

常见搭配

  • create a forensic image 制作取证镜像
  • forensic image acquisition 取证镜像采集
  • write blocker 写保护锁（做forensic imaging必备工具，防止写入原始盘）

例句

We are conducting forensic imaging of all systems seized from the site.
我们正在对现场扣押的所有系统主机进行取证镜像。

SLA和MTD的区别？

先分清两个缩写：

  • SLA = Service Level Agreement 服务级别协议（合同/承诺）
  • MTD = Maximum Tolerable Downtime 最大可容忍停机时间（业务底线，灾备/业务连续性）

    很多人会混淆 MTTD（Mean Time To Detect，平均检测时间，SOC取证常用），下面我一并说明

一句话核心区别

✅ SLA：服务商对客户的正式承诺（带罚则），说“我保证给你做到什么水平”
✅ MTD：业务自己的底线，说“超过这个停机时间，业务就扛不住了、损失不可接受”

SLA（Service Level Agreement）

  • 性质：协议、合同条款，甲乙双方约定
  • 视角：服务交付承诺
  • 例子：99.9%可用性、故障响应30分钟、工单4小时解决；达不到会有赔偿、扣服务费
  • 关注点：对外承诺、考核、赔付
  • 来源：IT服务、云服务商、外包合同

MTD（Maximum Tolerable Downtime）

  • 性质：业务风险阈值（业务影响分析BIA得出），不是对外合同
  • 视角：业务能扛多久
  • 定义：业务流程中断，到产生严重不可逆损失前，最长允许停机时长（NIST定义）
  • 关注点：业务生死线，用来倒推RTO、灾备架构
  • 关系：MTD ≥ RTO + 业务恢复时间；你的恢复能力必须在MTD之内
  • 例子：支付系统MTD=30分钟，停超30分钟资金损失、监管处罚就扛不住

对比表

项目 SLA MTD
全称 Service Level Agreement Maximum Tolerable Downtime
本质 服务合同承诺 业务容忍上限（风险指标）
给谁看 客户、外部甲方 内部业务、灾备团队
违约后果 罚款、赔付、扣服务费 业务重大损失、合规事故
用途 约定服务质量、考核供应商 设计灾备方案、定RTO
和RTO关系 SLA里经常写RTO作为承诺指标 MTD是RTO的上限红线

补充：MTTD（Mean Time To Detect，平均检测时间），网安取证/应急响应里高频出现：威胁从入侵成功到被发现，平均耗时。这是安全运营KPI，和上面两个完全不是一类东西，你前面看的forensic imaging取证场景里经常出现MTTD。

简单例子

电商结算系统：

  • 业务BIA评估：停机超过1小时，退款、客诉、监管处罚爆炸 → MTD=1小时
  • 找云厂商签合同：约定故障45分钟内恢复，可用性99.95%，超时赔付 → SLA=45分钟恢复
    👉 这里SLA（45min）必须小于MTD（60min），留安全余量。

配套全家桶（网安/灾备面试高频）

  • MTD：业务最多扛多久
  • RTO：目标恢复时间（系统恢复）
  • RPO：最多丢多久数据
  • SLA：对外承诺
  • MTTD：威胁多久才被发现
  • MTTR：发现后多久修好

SW-CMM

全称：Capability Maturity Model for Software，软件能力成熟度模型，常简称CMM
由美国卡内基梅隆大学软件工程研究所（SEI）推出，经典版本是1.1版（1993），现已被CMMI替代。

核心思想：把软件开发当作一套可管控、可持续改进的过程，用来评估软件公司的工程管理成熟度、减少项目失控、提升交付质量。

5个成熟度等级（阶梯式）

  1. Level 1 初始级（Initial）：混乱、靠个人英雄，无稳定流程，结果不可预测
  2. Level 2 可重复级（Repeatable）：项目级基础管理（需求、进度、配置、分包管理），同类项目能重复成功
  3. Level 3 已定义级（Defined）：组织层面建立统一、文档化的标准软件过程
  4. Level 4 已管理级（Managed）：量化管理，用数据度量过程、预测质量与偏差
  5. Level 5 优化级（Optimizing）：持续主动过程优化，主动识别缺陷、技术革新

和CMMI的区别

SW-CMM只针对软件；CMMI（能力成熟度集成模型）是它的升级版，融合软件、硬件、系统工程等多领域，是现在主流评估框架。

fail open（故障开放 / 故障放行）

一句话：校验/设备出错时，默认放行、允许通过，优先保证可用性
网络安全、访问控制、防火墙、阀门都在用这个术语，和 fail closed（故障关闭，fail secure） 是一对。

✅ 网安/软件场景（你做SOC会高频碰到）

防火墙、WAF、鉴权服务异常、引擎崩溃、超时、报错 → 流量/请求直接放过，不拦截

  • 优点：业务不断网、不宕机（优先保连通）
  • 风险：安全检查失效，恶意流量也进来了，安全降级

    例子：防火墙硬件挂了，Bypass 直通，就是典型 fail open

✅ 工控/阀门场景

气源/电力丢失 → 阀门自动打开，保证流体流通（冷却水、泄压、消防管路）

对比 fail closed（故障关闭，fail-secure）

  • fail open：故障 → 允许（优先可用）
  • fail closed：故障 → 阻断（优先安全）

安全最佳实践：鉴权、权限校验一般要求 fail closed，不能 fail open。

小补充

还有一个：fail last（故障保持），故障时维持故障前状态不变。

CI/CD

CI = Continuous Integration 持续集成
CD 有两层含义：Continuous Delivery 持续交付 / Continuous Deployment 持续部署
是一套软件工程、DevOps 的工程方法论，用来自动化构建、测试、发布软件，频繁、可靠地把代码变更交付到生产环境。

1、CI 持续集成（Continuous Integration）

核心：频繁把多人的代码合并到主干分支，自动做构建+测试，尽早发现问题

开发人员频繁（每天多次）将自己的代码提交合并到代码主干(main/master)；
每次提交触发自动化流程：

  1. 拉取最新代码
  2. 编译构建
  3. 运行单元测试、静态代码扫描、漏洞检测

目的

  • 避免“合并地狱”：很久才合并一次，一堆冲突、一堆bug
  • 尽早发现编译错误、单元测试失败、代码缺陷
  • 代码主干时刻保持可编译、可测试状态

CI 只管：合并‑构建‑测试，CI完成代表“软件包已经做好，质量经过基础校验”，不等于上线。

2、CD‑1：持续交付 Continuous Delivery

CI做完之后，自动产出可以随时部署的软件包；包准备好了，但是部署动作由人手动触发审批上线。

流程：开发提交 → CI（构建+测试）→ CD持续交付自动打包、做集成测试、UAT测试，产出就绪的发布包。
生产环境上线需要人工点击、审批后再发布。

特点：软件随时具备上线条件，但发布时机由人控制。适合金融、安全类对变更管控严格的系统。

3、CD‑2：持续部署 Continuous Deployment

在持续交付的基础上，全自动部署到生产，不需要人工干预。
代码过了CI全部测试，就自动一路跑到线上生产环境。

注意：
CI是基础；
持续交付：包自动做好，手动部署上线
持续部署：包自动做好，自动上线生产

完整CI/CD流水线典型链路

常用工具

  • GitLab CI、GitHub Actions、Jenkins、Azure DevOps、Tekton、ArgoCD（K8s场景）

通俗举例

没有CI/CD：大家各自写代码，半个月合并一次，手动编译、手动拷包，人工部署，经常出bug，出问题不知道是谁改坏的。
有CI/CD：每次提交代码机器自动编译、跑测试，有错立刻反馈给开发者；测试通过自动部署测试环境，审核后上线。

和安全结合（你做安全工程师相关）

CI/CD 中会嵌入安全环节，叫 DevSecOps：
在CI流水线中加入：SAST静态代码扫描、依赖漏洞扫描SCA、容器镜像扫描，代码还没上线就发现安全漏洞。

易考简答记忆版

CI持续集成：频繁合并代码，自动构建、自动测试，尽早暴露缺陷；
持续交付：生成随时可部署的软件版本，部署需要人工确认；
持续部署：在持续交付之上自动部署至生产环境。

lost update

丢失更新指的是会造成数据损坏的更新

关系数据库和NoSQL数据库有什么区别

一句话核心：
关系库：表结构固定、SQL查询、强事务（ACID）；NoSQL：结构灵活、不依赖SQL、横向扩容更容易，取舍一致性换性能/扩展性。

1、关系数据库（MySQL、PostgreSQL、Oracle、SQL Server）

模型：二维表（行+列），Schema预先定义，表之间用外键关联。
✅ 特点

  • 固定表结构，新增字段一般要改表（ALTER）
  • 使用标准SQL，支持JOIN多表联查
  • 支持 ACID 事务，适合强一致性场景（订单、支付、账务）
  • 支持约束：主键、外键、唯一、非空
  • 扩容难点：纵向扩容为主（升级服务器），分库分表比较复杂

❌ 短板

  • 数据结构一变就麻烦
  • 海量高并发、超大规模数据下扩展成本高
  • 嵌套、层次化数据存储很别扭

2、NoSQL（Not Only SQL），分成4大类

  1. 键值库 Key-Value：Redis、DynamoDB
  2. 文档库 Document：MongoDB、CouchDB（JSON/BSON文档，一条文档结构可以不一样）
  3. 列存储 Column-Family：Cassandra、HBase
  4. 图数据库 Graph：Neo4j（存节点、关系，适合社交、链路、风控图谱）

✅ 特点

  • Schema灵活，不需要预先定义结构，同集合里文档字段可以不一样
  • 天然容易水平分片横向扩展，适合海量数据、高吞吐
  • 大多默认是 BASE（基本可用、柔性状态、最终一致性），不保证强一致
  • 不擅长复杂JOIN；很多NoSQL没有事务，或事务能力有限

❌ 短板

  • 复杂多表关联查询麻烦
  • 强一致性场景容易踩坑
  • 没有统一查询语言，不同产品语法差异大

简明对比表

对比项 关系数据库 RDBMS NoSQL
数据模型 二维表，行、列、外键 文档/键值/列簇/图，无固定表结构
Schema 固定，预先定义 动态灵活
查询语言 标准SQL，支持JOIN 自有API/查询语法，大多不支持JOIN
事务 完整ACID，强一致性 大多最终一致性，事务支持弱
扩展方式 纵向扩容为主，分库分表复杂 天生横向分片，容易加机器
适用场景 支付、订单、财务、需要强关联强一致 日志、用户画像、缓存、IoT、海量高并发

典型选型例子

  • 用MySQL：交易系统、用户账号、订单、对账（钱不能错）
  • 用MongoDB：产品评论、用户行为、异构业务数据
  • 用Redis：缓存、计数器、会话
  • 用Neo4j：欺诈链路分析、社交关系、访问拓扑

网安/CTI场景补充

  • 告警规则、工单资产台账（强关联）：关系库合适
  • 海量原始日志、流量事件、遥测数据：NoSQL（Elasticsearch也算广义NoSQL）

CISSP简答背诵版

关系数据库采用预定义Schema的表结构，支持SQL查询与ACID事务，保证强一致性，适合结构化数据；NoSQL无固定Schema，分为文档、键值、列簇、图模型，优先支持水平扩展，通常为最终一致性，适合非结构化、海量高并发数据。

waterfall是什么软件开发方法？

Waterfall 瀑布模型（线性顺序开发模型）

一句话（CISSP背诵版）：传统线性SDLC方法，阶段串行，上一阶段签字完成，才能进入下一阶段；重文档、前期一次性锁定需求，几乎不支持迭代。

标准阶段（顺序固定）

  1. Requirements 需求收集与分析：敲定全部需求、产出SRS软件需求规格说明书，客户/甲方签字确认
  2. Design 系统设计：架构、模块、数据库、安全方案设计
  3. Implementation（Coding）编码实现：写代码
  4. Testing 测试：集成、系统、验收测试
  5. Deployment 部署上线
  6. Maintenance 运维维护

特点：阶段不重叠，像水流一层层往下落；正常不回头，中途改需求代价巨大

✅ 优点

  • 流程清晰、里程碑明确，方便管理、跟踪进度
  • 每个阶段强制产出文档，可追溯、合规性强（适合军工、政府、金融强监管项目）
  • 前期需求稳定时，预算、工期好预估
  • 权责清晰，适合外包、招投标项目

❌ 缺点（安全考点重点）

  • 反馈太晚：测试放在编码之后，漏洞、需求缺陷到项目末期才发现，返工成本极高（安全痛点）
  • 极度不灵活：需求一旦变更很难处理
  • 可用版本要等到最后阶段才能看到，客户中间看不到成果
  • 安全活动后置：安全评审、渗透测试大多在后期，不是左移（和DevSecOps刚好相反）

🆚 和 Agile（敏捷）快速对比

  • Waterfall：顺序、重文档、前期定死需求、交付晚、适合需求稳定合规项目
  • Agile：迭代增量、持续反馈、需求可以动态调整、频繁产出可用版本

适用场景

需求非常明确、几乎不会变动、法规强制完整文档和审批链路：航空、军工、医疗设备、部分香港政府合规项目。

如果你要，我把 Waterfall / Agile / Spiral / RAD 四个SDLC模型整理成一张CISSP速记对比表。

DevOps

CISSP背诵版：DevOps 是一套文化、实践与工具集合，打通开发（Dev）和运维（Ops），消除部门墙，依托自动化、CI/CD，缩短软件交付周期，实现高频、可靠的持续发布与持续反馈。

重点区分：敏捷（Agile）管怎么写代码；DevOps管从代码到上线、线上监控、故障闭环的全链路交付，敏捷可以和DevOps一起用。

核心思想

传统模式：开发写完丢给运维，两边互相甩锅、交接慢、上线周期很长。
DevOps：开发和运维共同对线上系统负责，不再是“开发交付、运维接盘”，责任共担；大量自动化，减少人工操作，发布可以一天多次。

核心实践（必考）

  1. CI/CD：持续集成、持续交付/部署（你前面学的）
  2. IaC 基础设施即代码：服务器、网络、配置写成代码，版本管理、自动部署（Terraform、Ansible）
  3. 配置管理：统一环境，避免“在我电脑上能跑”
  4. 持续监控、可观测性（Observability）：日志、指标、链路追踪，线上出问题立刻感知
  5. 快速回滚：发布出事，一键切回旧版本，降低故障影响
  6. 事后复盘（blameless postmortem，无责复盘）

DevOps 闭环循环（无限循环∞）

Plan 规划 → Build 开发 → Test 测试 → Release 发布 → Deploy 部署 → Operate 运维 → Monitor 监控 → 反馈回Plan

DevOps vs Agile vs Waterfall（速记）

  • Waterfall：串行、阶段隔离、周期长、需求前期定死
  • Agile：迭代开发，短sprint，聚焦开发侧，解决需求和代码迭代
  • DevOps：端到端打通开发+运维，自动化发布+线上运营，解决交付和运维侧，可以搭配敏捷

DevSecOps = DevOps + 安全：把安全扫描（SAST/SCA/镜像扫描）嵌入流水线，安全左移，安全不再是上线前最后一步单独审计，这是SOC非常高频的考点。

CALMS（DevOps经典框架，CISSP偶尔考）

  • Culture 文化（共享责任）
  • Automation 自动化
  • Lean 精益（减少浪费）
  • Measurement 度量（DORA四大指标）
  • Sharing 分享

DORA四大指标：

  1. 部署频率
  2. 变更前置时间（代码提交到上线多久）
  3. 变更失败率（发布后出问题比例）
  4. 故障恢复时间 MTTR

安全考点（对你SOC面试很有用）

DevOps发布很快，风险：人工安全评审跟不上、容易跳过安全检查；
解决方案：DevSecOps，自动化安全卡点进流水线，不通过就阻断发布。

Dirty Read 脏读（数据库事务隔离级别考点，CISSP / 数据库必考）

一句话背诵：一个事务读到了另一个事务还没提交（rollback可回滚）的修改数据。

举例子

事务A：更新余额 100 → 200，还没commit提交
事务B：读取余额，拿到 200（读到了未提交的数据）
然后事务A执行 rollback 回滚，余额变回100
👉 B读到的200就是脏数据，这个现象叫脏读

重点：读到未提交的数据

三个并发读问题放一起对比（配套记忆）

  1. Dirty Read 脏读：读到别的事务未提交的数据
  2. Non-repeatable Read 不可重复读：同一个事务内，两次读同一行，中间被别的事务提交修改，两次结果不一样（改了行）
  3. Phantom Read 幻读：同一个事务内，两次范围查询，别的事务提交新增/删除行，返回行数变了（新增消失）

SQL隔离级别（从低到高）

  1. Read Uncommitted（读未提交）：允许脏读、不可重复读、幻读
  2. Read Committed（读已提交，MySQL InnoDB默认）：禁止脏读，但会有不可重复读、幻读
  3. Repeatable Read（可重复读）：禁止脏读、不可重复读，仍可能幻读（InnoDB默认隔离级别）
  4. Serializable（串行化）：全部禁止，最高隔离，性能最差

极简口诀

脏读：读未提交；
不可重复读：行被改（已提交）；
幻读：行多了/少了（已提交新增删除）。

要不要我给你写一段面试简答标准答案？

Full SAFe

SAFe = Scaled Agile Framework，规模化敏捷框架；Full SAFe 是SAFe四种配置里最全、层级最高的一套配置

CISSP背诵版：Full SAFe是完整SAFe配置，包含Team、Program、Large Solution、Portfolio四层，用于超大型企业，同时管理复杂大系统+投资组合与战略对齐，覆盖全部7项业务敏捷核心能力

SAFe一共4种配置（由简到全）

  1. Essential SAFe（基础版）：Team + Program，单条ART敏捷发布火车，入门标配
  2. Large Solution SAFe（大型解决方案版）：Team + Program + Large Solution，多条ART一起做超复杂系统（军工、大型设备），没有投资组合管理
  3. Portfolio SAFe（投资组合版）：Team + Program + Portfolio，把多个ART对齐公司战略、精益预算
  4. Full SAFe（完整版）：四层全部集齐：Team + Program + Large Solution + Portfolio
    ✅ 同时具备：大型复杂系统交付能力 + 公司投资组合、战略、精益资金治理

适用场景

千人级、集团型、多产品线、跨地域的大型组织，比如金融、军工、政府、大型科技集团，同时有多个互相依赖的大型产品/项目，需要顶层战略一直对齐到一线开发交付。

四层简要含义

  • Team 团队层：单个敏捷小组（Scrum）
  • Program 项目群层：ART敏捷发布火车，PI规划
  • Large Solution 大型解决方案层：协调多个ART，做系统集成、系统工程
  • Portfolio 投资组合层：战略、资金分配、价值流治理、投资优先级

一句话区分

  • Essential：一条ART，小团队集群
  • Large Solution：很多ART一起做一个巨大系统，不管顶层预算
  • Portfolio：管战略和钱，不一定是超复杂系统
  • Full SAFe：既要做多个巨型复杂系统，又要顶层战略和投资管控

考点提醒：SAFe是规模化敏捷，用来把敏捷从几个团队放大到整个大企业；和普通敏捷、瀑布并列在SDLC考题里。
